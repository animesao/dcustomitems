## Что такое плейсхолдер

**Плейсхолдер** — это «дырка» в тексте, которая заполняется живыми данными в момент показа.

Например, текст:

```text
Здоровье: %dci_health% / %dci_max_health%
```

Игроку с 15 сердечками покажут:

```text
Здоровье: 15 / 20
```

Сам текст один и тот же для всех — меняются только подставленные значения. Это удобно: не нужно писать отдельную строку для каждого игрока и каждого случая.

Плейсхолдеры нужны везде, где текст зависит от игрока: чат, табличка, меню, право, титул, лор.

## Что такое PlaceholderAPI

**PlaceholderAPI** — это отдельный плагин, который служит «единым справочником» плейсхолдеров.

Схема простая:

```text
DeluxeMenus (или любая табличка)   →   «Дай мне текст с %dci_health%»
                                        ↓
                                    PlaceholderAPI
                                        ↓
                     «Дай мне текст, где %dci_health% = 15»
```

PlaceholderAPI не знает про DC-CustomItems и наоборот. Он просто спрашивает у всех установленных плагинов: «что такое %dci_health%?», и возвращает ответ.

### Установка

1. Скачайте PlaceholderAPI (на [Modrinth](https://modrinth.com/plugin/placeholderapi) или [SpigotMC](https://www.spigotmc.org/resources/placeholderapi.6245/)).
2. Положите `PlaceholderAPI-*.jar` в папку `plugins/`.
3. Перезапустите сервер.
4. Проверьте, что всё работает:

```bash
/papi
```

— команда покажет список подключённых расширений. В нём должно быть **DC-CustomItems**.

### Почему PlaceholderAPI необязателен

В `plugin.yml` плагина PlaceholderAPI указан в `softdepend`:

```yaml
softdepend:
  - PlaceholderAPI
  - Vault
```

**`softdepend`** означает: «если этот плагин есть — подожди его и используй; если нет — работай и без него». Плагин **не сломается** без PlaceholderAPI.

Но без него:

- плейсхолдеры **не будут** подставляться в чужих плагинах (табличках, меню, чат-плагинах);
- плейсхолдеры **не будут** подставляться в сообщениях самого DC-CustomItems.

Если PlaceholderAPI установлен, в консоли при старте вы увидите:

```text
PlaceholderAPI found!
[PlaceholderAPI] Exported placeholders registered!
```

Если этих строк нет — проверьте, что `PlaceholderAPI.jar` лежит в `plugins/`, и перезапустите сервер (не только `/ci reload`).

### Как плагин подключается к PlaceholderAPI

Отдельный класс `DCIPlaceholderExpansion` отвечает за связь с PlaceholderAPI.

| Что | Значение |
|-----|----------|
| Идентификатор расширения | `dcustomitems` — именно под этим именем расширение регистрируется в PlaceholderAPI |
| Автор | `animesao` |
| Версия | берётся из версии плагина |
| `persist()` | `true` — расширение остаётся зарегистрированным, даже если PlaceholderAPI перезагрузится |
| Как определяется тип файла | Если плагин видит в `.java` строку `extends CustomPlaceholder` — файл считается плейсхолдером |

### Как записывать плейсхолдер

Есть две формы записи. Обе используются в примерах и в документации плагина:

| Форма | Пример | Комментарий |
|-------|--------|-------------|
| Короткая | `%dci_health%` | Так плейсхолдеры записаны в README плагина и в примерах |
| Полная | `%dcustomitems_health%` | Под этой формой расширение реально зарегистрировано в PlaceholderAPI |

Почему так: PlaceholderAPI ищет расширение по первой части имени до подчёркивания. Расширение зарегистрировано под именем `dcustomitems`, поэтому подставляется `%dcustomitems_health%`. Короткая запись `%dci_health%` требует расширения с именем `dci`.

Проверить, какая форма работает у вас, можно прямо на сервере:

```bash
/papi parse %dcustomitems_health%
/papi parse %dci_health%
```

Если команда вернула `15` — форма работает. Если вернула сам текст `%dci_health%` — используйте полную форму `%dcustomitems_health%`.

> **Совет.** В своих конфигах безопаснее писать полную форму — она работает всегда. Короткую удобно использовать в текстах, где вы точно знаете, что она подставится.

## Плейсхолдеры игрока

Эти плейсхолдеры показывают данные конкретного игрока. Работают, только когда в тексте известен игрок.

| Плейсхолдер | Что возвращает | Пример |
|-------------|----------------|--------|
| `%dci_player%` | Имя игрока | `Steve` |
| `%dci_player_uuid%` | UUID игрока | `8667ba71-…` |
| `%dci_display_name%` | Отображаемое имя (с цветами) | `§aSteve` |
| `%dci_health%` | Текущее здоровье (целое число) | `15` |
| `%dci_max_health%` | Максимальное здоровье | `20` |
| `%dci_health_percent%` | Здоровье в процентах (0–100) | `75` |
| `%dci_food%` | Уровень сытости (0–20) | `18` |
| `%dci_saturation%` | Насыщение (целое) | `5` |
| `%dci_level%` | Уровень опыта | `30` |
| `%dci_exp%` | Процент опыта (0–100) | `42` |
| `%dci_x%` | Координата X (целая) | `100` |
| `%dci_y%` | Координата Y (целая) | `64` |
| `%dci_z%` | Координата Z (целая) | `-200` |
| `%dci_world%` | Имя мира | `world` |
| `%dci_gamemode%` | Режим игры | `SURVIVAL` |
| `%dci_fly_status%` | Включён ли полёт | `on` / `off` |
| `%dci_item_in_hand%` | Материал предмета в основной руке (или `AIR`, если рука пуста) | `DIAMOND_SWORD` |
| `%dci_online%` | Сколько игроков онлайн | `15` |
| `%dci_max_players%` | Максимум игроков на сервере | `50` |

## Плейсхолдеры плагина

Эти плейсхолдеры показывают состояние самого плагина.

| Плейсхолдер | Что возвращает | Пример |
|-------------|----------------|--------|
| `%dci_version%` | Версия плагина | `1.333.0` |
| `%dci_item_count%` | Сколько YAML-предметов загружено | `12` |
| `%dci_java_item_count%` | Сколько Java-предметов загружено | `3` |
| `%dci_command_count%` | Сколько команд зарегистрировано | `2` |
| `%dci_placeholder_count%` | Сколько плейсхолдеров зарегистрировано | `1` |
| `%dci_module_count%` | Сколько модулей загружено | `4` |
| `%dci_database_type%` | Тип базы данных | `sqlite`, `mysql`, `none` |
| `%dci_active_effects%` | Активные эффекты от предметов | `SPEED:II, STRENGTH:I` или `none` |
| `%dci_active_effects_count%` | Сколько активных эффектов | `2` |

> `%dci_active_effects%` показывает эффекты, которые дают **предметы плагина**, а не зелья игрока.

## Предметные плейсхолдеры

Эти плейсхолдеры отвечают на вопрос «есть ли у игрока конкретный предмет».

### Синтаксис

```text
%dci_has_<id>%          — есть ли предмет где-нибудь в инвентаре
%dci_holding_<id>%      — держит ли игрок предмет в руке
%dci_equipped_<id>%     — надет ли предмет в слот активации
%dci_item_amount_<id>%  — сколько всего предметов в инвентаре
```

| Плейсхолдер | Что проверяет | Возвращает |
|-------------|---------------|------------|
| `has_` | Весь инвентарь: основные слоты, броня, вторая рука | `true` / `false` |
| `holding_` | Основная рука **или** вторая рука | `true` / `false` |
| `equipped_` | Слот активации предмета (`HAND`, `OFFHAND`, `HEAD`, `CHEST`, `LEGS`, `FEET`) | `true` / `false` |
| `item_amount_` | Количество предметов с таким id в инвентаре | число (`0`, `3`, …) |

Примеры:

```text
%dci_has_vampire-blade%        → true
%dci_holding_vampire-blade%    → false
%dci_equipped_vampire-blade%   → false
%dci_item_amount_vampire-blade% → 3
```

`<id>` — это id предмета: тот же ключ, под которым предмет лежит в YAML-файле или задан в Java-классе. Регистр не важен.

### Как разбирается id с подчёркиваниями

Тут есть тонкость. Плейсхолдер и id предмета разделены одним и тем же подчёркиванием, поэтому id может содержать подчёркивания — например, `fire_resistance_potion`.

Плагин разбирает такой id так:

1. Сначала ищет **точное совпадение** — весь остаток строки целиком.
2. Если совпадения нет — отбрасывает кусок после **последнего** подчёркивания и пробует снова.
3. И так дальше, пока подчёркивания не кончатся.

Пример. Пусть есть предметы `vampire-blade` и `fire_resistance_potion`:

| Запрос | Остаток | Шаг 1 (точно) | Шаг 2 | Шаг 3 | Итог |
|--------|---------|---------------|--------|--------|------|
| `%dci_has_vampire-blade%` | `vampire-blade` | нашли | — | — | `vampire-blade` |
| `%dci_has_fire_resistance_potion%` | `fire_resistance_potion` | нашли | — | — | `fire_resistance_potion` |
| `%dci_has_fire_resistance%` | `fire_resistance` | нет | `fire` | нет | предмета нет → текст остаётся |

Что из этого следует:

| Правило | Пояснение |
|---------|-----------|
| Сначала побеждает **самое длинное** совпадение | Точное совпадение проверяется раньше укороченных |
| Ищутся и YAML-предметы, и Java-предметы | Оба вида попадают в общий список id |
| Нет предмета с таким id | Плейсхолдер остаётся текстом (`%dci_has_что-то%`), а не превращается в `false` |
| Одинаковые окончания могут путать | Если есть `sword` и `sword_of_dawn`, то `%dci_has_sword_of_dawn%` найдёт именно `sword_of_dawn` (точное совпадение), а `%dci_has_sword%` — `sword` |

## Глобальные плейсхолдеры

**Глобальный плейсхолдер** — тот, который не зависит от игрока. Его можно использовать в текстах, где игрока нет: в логе, в консоли, в сообщении для всех.

Когда PlaceholderAPI запрашивает значение и игрока в запросе нет, плагин отдаёт только эти:

| Плейсхолдер | Что возвращает |
|-------------|----------------|
| `%dci_version%` | Версия плагина |
| `%dci_item_count%` | Количество YAML-предметов |
| `%dci_online%` | Игроков онлайн |
| `%dci_max_players%` | Максимум игроков |

Остальные плейсхолдеры в «глобальном» запросе не подставляются — им нужен игрок.

## Свои плейсхолдеры

Плейсхолдер — это обычный `.java`-файл в папке `items/`, класс наследует `CustomPlaceholder`.

Требования к файлу:

| Требование | Почему |
|------------|--------|
| Класс `public` и наследует `CustomPlaceholder` | По строке `extends CustomPlaceholder` плагин определяет тип файла |
| Публичный конструктор без аргументов | Плагин создаёт плейсхолдер через `new` без параметров |
| В конструкторе вызван `super("имя")` | Это имя и есть идентификатор плейсхолдера |

### Полный рабочий пример

Файл `plugins/DC-CustomItems/items/kills-placeholder.java`:

```java
import me.dcplugin.dcustomitems.api.placeholders.CustomPlaceholder;
import org.bukkit.entity.Player;

import java.util.HashMap;
import java.util.Map;
import java.util.UUID;

/**
 * Счётчик убийств игрока.
 *
 * Плейсхолдер: %dcustomitems_kills% (короткая запись — %dci_kills%)
 *
 * Что делать: положите файл в plugins/DC-CustomItems/items/
 * и выполните /ci reload.
 */
public class KillsPlaceholder extends CustomPlaceholder {

    // Простое хранилище в памяти.
    // В настоящем проекте данные берутся из базы — см. раздел «База данных».
    private static final Map<UUID, Integer> KILLS = new HashMap<>();

    public KillsPlaceholder() {
        super("kills");   // ← идентификатор: префикс dci_ сюда НЕ добавляем
    }

    @Override
    public String getValue(Player player) {
        // player может быть null — тогда возвращаем что-то нейтральное
        if (player == null) return "0";
        return String.valueOf(KILLS.getOrDefault(player.getUniqueId(), 0));
    }

    /** Вызывается из вашего кода, когда игрок кого-то убил. */
    public static void addKill(Player player) {
        KILLS.merge(player.getUniqueId(), 1, Integer::sum);
    }
}
```

После `/ci reload` в консоли появится:

```text
[API] Loaded: 0 items, 0 commands, 1 placeholders, 0 modules
```

И плейсхолдер станет доступен как `%dcustomitems_kills%`.

### Правило getIdentifier

| Правило | Пример |
|---------|--------|
| Идентификатор задаётся в конструкторе: `super("имя")` | `super("kills")` |
| Он автоматически приводится к нижнему регистру | `super("Kills")` → `kills` |
| В идентификатор **не** добавляется префикс `dci_` | `super("dci_kills")` — неправильно, получится `%dcustomitems_dci_kills%` |
| Идентификатор не должен быть пустым | `super("")` — плейсхолдер работать не будет |
| Метод `getIdentifier()` можно переопределить, но обычно не нужно | — |

Если ваш идентификатор совпадёт с встроенным плейсхолдером (например, `health`), **ваш** вариант победит: Java-плейсхолдеры проверяются раньше встроенных.

### Как читается значение

Значение читает метод:

```java
public abstract String getValue(Player player);
```

| Правило | Пояснение |
|---------|-----------|
| Метод вызывается каждый раз, когда кто-то запросил плейсхолдер | Не кэшируйте «навсегда» — возвращайте актуальное значение |
| `player` может быть `null` | Для глобальных запросов. Всегда проверяйте на `null` |
| Метод должен возвращать строку | `String.valueOf(...)`, а не число |
| Запрос может прийти из другого потока PlaceholderAPI | Не меняйте общие структуры без синхронизации; тяжёлые запросы к базе кэшируйте |
| Ошибка внутри метода не ломает сервер | Плагин залогирует её и вернёт пустое значение |

Дополнительно есть два необязательных метода:

| Метод | Когда вызывается |
|------|------------------|
| `void onRegister()` | Плейсхолдер зарегистрирован (старт сервера или `/ci reload`) |
| `void onUnregister()` | Плейсхолдер снимается (перед `/ci reload` или при выключении плагина) |

## Где работают плейсхолдеры

### В сообщениях плагина

Сообщения DC-CustomItems проходят через `ColorUtils.processMessage(player, text)` — а он подставляет плейсхолдеры PlaceholderAPI **автоматически**. Ничего дополнительно делать не нужно.

Так работают, например:

- сообщения предмета: `equip-message`, `unequip-message`, `cooldown-message`, `uses-depleted-message`, `max-duration-message`;
- сообщения действий: `message`, `title`, `actionbar`, `broadcast`;
- центральная система сообщений (см. [Сообщения](11-messages.md)) — там, где текст берётся с игроком.

Пример в YAML-предмете:

```yaml
my-sword:
  item:
    type: DIAMOND_SWORD
    title: '&bМеч рыцаря'

  equip-message: '&aHP: %dci_health%/%dci_max_health% &7| &bУровень: %dci_level%'
  cooldown-message: '&cКулдаун: {seconds}с &7| &bЗдоровье: %dci_health%'
```

> **Важно про `{...}` и `%...%`.** Скобки `{seconds}`, `{item}`, `{player}` — это внутренние подстановки самого плагина. Проценты `%dci_...%` — это плейсхолдеры PlaceholderAPI. Не путайте их.

### В лоре и названии предмета

Здесь есть ограничение, о котором важно знать.

| Место | Что подставляется |
|-------|-------------------|
| Название и лор предмета (`title`, `lore`) | **Только** `%cooldown%` и `%uses%` — собственные плейсхолдеры плагина. `%cooldown%` — время до готовности, `%uses%` — оставшиеся заряды (или `∞`, если зарядов бесконечно много) |
| Сообщения предмета | Плейсхолдеры PlaceholderAPI — работают |

Название и лор — это **статичный** текст: он записывается в предмет один раз при загрузке и больше не меняется. Поэтому подставить туда «здоровье игрока» нельзя — оно неизвестно в момент создания предмета.

Если вам нужен текст, зависящий от игрока, — делайте это через **сообщения** (например, `equip-message`), а не через лор.

### В конфигах других плагинов

Здесь плейсхолдеры работают как обычно — через PlaceholderAPI:

```yaml
# Пример: DeluxeMenus, меню
title: "&6Мой профиль"
items:
  13:
    material: PLAYER_HEAD
    name: "&a%dcustomitems_player%"
    lore:
      - "&7Здоровье: &e%dcustomitems_health%&7/&e%dcustomitems_max_health%"
      - "&7Онлайн: &e%dcustomitems_online%"
```

Тот же принцип работает в:

- табличках (через плагины вроде EssentialsX);
- чат-плагинах (ChatManager, Towny и подобные);
- системах прав (LuckPerms, PlaceholderAPI-шаблоны);
- меню (DeluxeMenus, DeluxeMenuX из модуля — см. [Модули](10-modules.md));
- списках, таблицах, счётах (scoreboard-плагины).

## Частые ошибки

| Симптом | Причина | Что делать |
|---------|---------|------------|
| Плейсхолдер остался текстом `%dci_health%` | Нет PlaceholderAPI | Поставьте PlaceholderAPI и перезапустите сервер |
| Плейсхолдер остался текстом | Неправильный префикс | Попробуйте полную форму `%dcustomitems_health%` |
| Плейсхолдер остался текстом | Опечатка в имени | Имена регистронезависимы, но пишутся через `_`: `%dci_health_percent%`, а не `%dci_healthPercent%` |
| `%dci_has_что-то%` остался текстом | Предмета с таким id нет | Проверьте id предмета; чужие id (не из `items/`) так не работают |
| Плейсхолдер не подставляется в лоре | Лор статичный | Перенесите текст в `equip-message` или другое сообщение |
| Плейсхолдер подставляется не у того игрока | Запрос без игрока | Глобальные запросы поддерживают только 4 плейсхолдера — см. [Глобальные плейсхолдеры](#глобальные-плейсхолдеры) |
| Свой плейсхолдер не появился после reload | Ошибка компиляции файла | Смотрите консоль: `[JavaCompiler] ❌ файл:строка - …` |
| Свой плейсхолдер появился, но показывает старое | `getValue` возвращает кэш | Значение читается при каждом запросе — обновляйте источник данных |
