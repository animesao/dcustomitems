# 02. Как это работает

> **Что ты узнаешь:** из чего состоит плагин, что происходит при старте и при
> `/ci reload`, как файл превращается в предмет в игре и почему всё это
> устроено именно так.
>
> **Предусловия:** [Установка](01-getting-started.md) выполнена, плагин в консоли
> пишет `CustomItems enabled!`.

## Главная идея

Плагин — это **движок**, а не набор готовых предметов. Всё, что игрок видит,
описано в обычных файлах, которые вы кладёте в папку `items/`.

```
ваш .yml / .java  →  плагин читает  →  предмет в игре
```

Три следствия:

1. **Чтобы добавить предмет, не нужен веб-панель, не нужен `/give` с
   консоли, не нужно перезагружать сервер.** Кладёте файл, пишете `/ci reload`.
2. **Чтобы убрать предмет, достаточно удалить файл.** Никаких «списков
   предметов», которые надо сверять с конфигом.
3. **Ошибка в вашем файле не ломает плагин.** Сломанный YAML или `.java`
   пропускается, в консоль пишется причина, остальные предметы работают.

## Карта файлов

```
plugins/DC-CustomItems/
├── config.yml             # настройки самого плагина
├── items/                 # ← всё, что вы настраиваете
│   ├── messages.java      # все тексты плагина
│   ├── runes.yml          # предметы (можно несколько в одном файле)
│   ├── give.java          # команда
│   └── shop/              # модуль — папка
│       ├── config.yml
│       └── shop.java
├── cache/                 # хеши файлов (чтобы не компилировать заново)
├── compiled/              # готовые .class
├── data.db                # база SQLite
├── logs/                  # логи (если включён file-logging)
└── backups/               # копии перед /ci reload
```

**Разница между `items/` и `config.yml`:** в `config.yml` — настройки
движка (база данных, бэкапы, сеты бонусов), в `items/` — ваш контент.
Сеты бонусов — исключение: они описаны в `config.yml`, потому что относятся
к движку, а не к предмету.

## Что происходит при старте

По порядку (как в коде `PluginBootstrap.enable()`):

| # | Шаг | Что делает |
|---|-----|-----------|
| 1 | `saveDefaultConfig()` | Создаёт `config.yml`, если его нет |
| 2 | `createDefaultMessagesFile()` | Создаёт `items/messages.java`, если его нет |
| 3 | `checkConfigMigration()` | Сообщает в консоль, если в `config.yml` остались старые предметы |
| 4 | `initFileLogging()` | Подключает файловый лог, если `file-logging: true` |
| 5 | `initManagers()` | Создаёт менеджеры (предметы, эффекты, атрибуты, сеты) |
| 6 | `initPlaceholders()` | Создаёт менеджер плейсхолдеров и регистрирует расширение PAPI |
| 7 | `ItemRegistry.loadAll()` | **Читает `items/`**: JAR-файлы, `.java`-файлы, рецепты, применяет `messages.java` |
| 8 | `itemHandler.loadCustomItems()` | **Читает YAML-предметы** и регистрирует их рецепты |
| 9 | `registerJavaRecipes()` | Регистрирует рецепты Java-предметов (теперь YAML уже загружен — рецепт может ссылаться на YAML-предмет) |
| 10 | `moduleManager.loadAll()` | Находит папки-модули в `items/` и включает их |
| 11 | `registerBukkitCommand()` | Регистрирует `/ci` |
| 12 | `registerEvents()` | Подписывает слушатели Bukkit |
| 13 | `initDatabase()` | Открывает `data.db` (SQLite) или поднимает пул MySQL |
| 14 | `EquippedItemsChecker.start()` | Запускает глобальный таск проверки экипировки |
| 15 | `checkUpdates()` | Фоново проверяет GitHub на новую версию |

Обратите внимание на порядок 7→8→9: **сначала** грузятся Java-предметы,
**потом** YAML, **потом** рецепты Java-предметов. Это позволяет рецепту
ссылаться и на YAML-предмет, и на Java-предмет в любом направлении.

## Что происходит при `/ci reload`

```
1. Бэкап items/ (если backup.on-reload: true)
2. Перечитывание config.yml
3. Выгрузка модулей
4. Снятие команд из CommandMap
5. onUnregister() у команд и плейсхолдеров
6. Очистка реестров (предметы, команды, плейсхолдеры, модули)
7. Перечитывание items/ — всё заново
8. onRegister() у команд и плейсхолдеров
9. Повторная регистрация команд
10. Загрузка модулей
```

**Важные свойства:**

- Всё, что не в `items/`, после reload **исчезает**. Случайно созданный
  `.java`-файл с ошибкой не «залипает».
- Классы перекомпилируются только если файл изменился (сверка по MD5).
  Неизменённые файлы берутся из кэша — reload быстрый.
- Всё происходит на **главном потоке** сервера. На большом сервере reload
  может занять доли секунды — это нормально, но не делайте его в цикле.

## Путь файла до предмета в инвентаре

Для YAML-предмета:

```
items/runes.yml
   │  ItemLoader читает файл, парсит секцию «rune-of-life»
   │  создаёт ItemStack (материал, имя, лор, зачарования)
   │  и ставит PDC-метку custom_item_id = "rune-of-life"
   ▼
ItemStack в инвентаре игрока
   │  любой предмет, у которого в PDC лежит custom_item_id,
   │  плагин узнаёт по id и достаёт описание из реестра
   ▼
Эффекты / действия / триггеры
```

**PDC** (Persistent Data Container) — это «бирка» внутри предмета, которая
переживает перезапуск сервера и не копируется при клонировании в
большинстве плагинов. Именно поэтому предмет остаётся «кастомным» после
рестарта.

---

## Как предмет узнаётся

```java
String id = item.getItemMeta()
                 .getPersistentDataContainer()
                 .get(customItemKey, PersistentDataType.STRING);
```

Один `getItemMeta()` — и id известен. Дальше плагин ищет описание:

- сначала среди YAML-предметов,
- если не нашлось — среди Java-предметов.

Если id не найден нигде (например, предмет остался от удалённого YAML) —
плагин считает его обычным и просто игнорирует.

**Важно:** id пишется в предмет **один раз**, при создании. Если вы
переименуете предмет в YAML, старые экземпляры в инвентарях останутся со
старым id и перестанут работать. Переименовывайте аккуратно.

## Что такое «слот активации»

У каждого предмета есть `activation-slot` — слот, в котором он «работает»:

| Слот | Что это |
|------|---------|
| `HAND` | Основная рука |
| `OFFHAND` | Вторая рука |
| `HEAD` | Шлем |
| `CHEST` | Нагрудник |
| `LEGS` | Поножи |
| `FEET` | Ботинки |

Предмет даёт эффекты, атрибуты и срабатывает по триггерам **только когда он
лежит в своём слоте**. Предмет в сумке ничего не делает.

Значение по умолчанию — `HAND`. Проверить можно командой
[`/ci debug <id>`](08-commands.md).

## Кэш и компиляция

**YAML** перечитывается всегда — он дешёвый.

**Java** компилируется заново только при изменении файла:

```
cache/file_hashes.properties   →  "items/shop/shop.java" = <md5>
```

Если MD5 совпал — берём готовый `.class` из `cache/`. Это и делает reload
быстрым при большом количестве Java-файлов.

**Ограничения компилятора** (защита от случайной перегрузки сервера):

| Ограничение | Значение |
|-------------|----------|
| Максимум `.java`-файлов | 300 |
| Максимум размера одного файла | 512 КБ |

При превышении файлы пропускаются, в консоль пишется причина.

## Модули

Модуль — это **папка** в `items/`:

```
items/shop/
├── config.yml     # настройки модуля
└── shop.java      # код модуля
```

Любая папка в `items/` (кроме `EXAMPLE-*`, `EXAMPLES`, `_template`) — это
модуль. Он находит свой `config.yml`, читает команды и плейсхолдеры из
настроек и вызывает `onEnable()`.

Команды модуля регистрируются в `CommandMap` сервера и **снимаются** при
выгрузке модуля — «мёртвые» команды не остаются.

Подробно — [Модули](10-modules.md).

## Горячая перезагрузка: что можно и что нельзя

| Можно на горячую | Нельзя (нужен рестарт) |
|------------------|------------------------|
| YAML-предметы | Смена типа базы данных (SQLite ⇄ MySQL) |
| Java-предметы, команды, плейсхолдеры | `java-compilation: true ⇄ false` |
| Модули | Обновление самого плагина (jar) |
| Рецепты | Изменение namespace (plugin.yml) |
| Тексты в `items/messages.java` | |
| `config.yml` (кроме `database.*`) | |

**Почему нельзя менять `java-compilation` на горячую:** флаг читается при
старте, и при `false` компилятор вообще не запускается — переключение
требует перезапуска, чтобы загрузить новые классы.

## Производительность

Плагин рассчитан на большие серверы. Основные решения:

| Что | Как |
|-----|-----|
| Проверка экипировки | **Один** глобальный таск на весь сервер, а не по таску на игрока. Каждый игрок пересчитывается не чаще раза в 150 мс, и только если состав слотов изменился (сверка по хешу) |
| Чтение мета-предметов | PDC всех слотов игрока читается **один раз** за 150 мс и переиспользуется |
| Кулдауны и счётчики | В памяти (`ConcurrentHashMap`), чистятся при выходе игрока |
| Эффекты | Суммируются в карту и применяются одним проходом, а не по предмету |
| Плейсхолдеры | Кэшируются; список ID предметов пересобирается только при изменении состава |
| Проверка обновлений | В отдельном потоке, с таймаутом 10 с |
| База данных | Готовые async-методы, чтобы не блокировать главный поток |

**Что может тормозить сервер (ваша ответственность):**

- тяжёлые действия в триггере `on_move` (срабатывает очень часто);
- SQL-запросы в триггерах — используйте async-методы;
- большой радиус у AoE-действий (`damage_nearby` с радиусом 50).

Подробнее — [Решение проблем](17-troubleshooting.md).

## Почему так, а не иначе

**Почему предметы — файлы, а не код плагина?**
Чтобы админ мог добавить предмет, не собирая jar, и чтобы «сломанный»
предмет не ломал весь плагин.

**Почему Java-файлы компилируются на сервере?**
Чтобы не нужен был Maven и внешняя сборка: положил файл — сделал `/ci reload`.

**Почему всё в одном `items/`, а не в разных папках?**
Одно место = одно правило. Модуль — это тоже папка в `items/`, предмет — тоже
файл в `items/`. Никаких отдельных «папок с предметами», которые надо
помнить.

**Почему `items/messages.java` — это Java, а не YAML?**
Чтобы сообщения поддерживали логику: префиксы, конкатенацию, вычисления. И
потому, что этот файл и так компилируется движком — отдельный механизм
загрузки не нужен.

**Почему примеры не устанавливаются автоматически?**
Новичок получает чистую папку и один файл, а не 90 файлов, о которых он
ничего не знает. Примеры — в репозитории, копируются руками.
