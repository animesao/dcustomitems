# Права (permissions)

## Что ты узнаешь

- что такое «право» (permission node) в Minecraft и кто его выдаёт;
- полный список узлов, которые проверяет DC-CustomItems, — что каждый разрешает и у кого он есть по умолчанию;
- чем отличается право предмета (`permission:` в YAML) от права команды (конструктор `CustomCommand`);
- как выдать право только одному конкретному предмету;
- готовые команды LuckPerms для типовых задач;
- какие права есть у самого плагина по умолчанию (только у операторов).

## Предусловия

- Плагин DC-CustomItems установлен, сервер запускается — см. [Установка](01-getting-started.md).
- Вы умеете выдавать права оператору (`/op`) — это умеет любой сервер.
- Для работы с правами по группам вам понадобится плагин прав — например [LuckPerms](https://luckperms.net/).
- Общий список страниц — в [Содержании вики](README.md).

## Что такое право

**Право** (в Minecraft оно называется *permission node*, то есть «узел права») — это строка-имя, например `dcustomitems.reload`.

Логика простая: плагин спрашивает «есть ли у игрока право `X`?» и в зависимости от ответа пускает или не пускает.

| Понятие | Что это |
|---------|---------|
| Узел права | Строка-имя. Обычно пишут через точку: `dcustomitems.reload`, `myplugin.use` |
| Иерархия | Точка в имени — это не структура, а просто соглашение. В LuckPerms точка работает как разделитель групп, но в самом Bukkit узлы независимы |
| `*` | «Любое право». В Bukkit это особое значение: игрок с правом `*` проходит любую проверку |
| Оператор (`op`) | Игрок с правами оператора. По умолчанию у него есть почти все права, объявленные плагинами |
| Плагин прав | LuckPerms, GroupManager, PermissionsEx. Позволяют выдавать права группам и отдельным игрокам, без `/op` |

Права нужны, чтобы:

- обычные игроки не могли перезагружать плагин (`/ci reload`);
- дорогой предмет нельзя было использовать всем подряд;
- админскую команду модуля нельзя было выполнить случайно.

## Кто какие права имеет

| Кто | Какие права есть по умолчанию |
|-----|------------------------------|
| Оператор (`/op`) | Почти все: в том числе `dcustomitems.reload` |
| Обычный игрок | Никаких, кроме тех, что вы выдали |
| Владелец сервера (владелец файла `ops.json`) | Как у оператора |

Когда плагин объявляет право с `default: op`, Bukkit сам выдаёт его операторам. Права без `default` не выдаются **никому** — даже оператору, — если только плагин не проверяет `isOp()` отдельно.

Выдать права вручную:

```bash
# Сделать оператором — он получит почти всё
/op Steve

# Выдать конкретное право (если стоит плагин прав)
/lp user Steve permission set dcustomitems.reload true
```

## Полная таблица прав плагина

Ниже — **все** узлы, которые DC-CustomItems проверяет где-либо в своём коде.

| Узел права | Что разрешает | Кто имеет по умолчанию |
|------------|---------------|-------------------------|
| `dcustomitems.reload` | Выполнять `/ci reload`, `/ci validate`, `/ci debug <id>`, `/ci backup` | Оператор (объявлено в `plugin.yml` с `default: op`) |
| `customitems.admin` | Получать при входе служебное сообщение администратора о доступной новой версии | Никто: узел не объявлен в `plugin.yml`, поэтому выдаётся только вручную. Проверяется вместе с `isOp()` и правом `*` |
| `customitems.update` | Получать оформленное уведомление о новой версии при входе | Никто. Узел не объявлен, выдаётся только вручную. Проверяется в `UpdateChecker` — на данный момент метод уведомления сервером не вызывается, поэтому на практике узел ничего не делает |
| `dci.<имя_команды>` | Использовать команду модуля, зарегистрированную через `registerDynamicCommand` | Никто: право назначается модулем при регистрации команды и выдаётся вручную |
| `permission:` в YAML-предмете | Использовать **этот предмет**: клик, надевание (эффекты/атрибуты/сеты) и все триггеры | Никто: если ключ не задан — ограничений нет вообще |
| Право из конструктора `CustomCommand` | Выполнять **эту команду** | Никто: если в конструкторе не задано право — команда доступна всем |
| Права из `permissions:` в `config.yml` модуля | Ничего сами по себе: это **объявление** прав модуля (для документации и для плагина прав) | Никто |

> Таблица покрывает только встроенную часть плагина. У образцов модулей есть свои узлы — например `dci.balance`, `dci.pay`, `dci.eco`, `dci.craft`, `deluxemenux.admin`. Их задаёт автор модуля, и они работают только если модуль включён (то есть лежит в `items/` без префикса `EXAMPLE-`).

### Права команд и служебные

Подробнее про `dcustomitems.reload`:

| Подкоманда | Что делает | Право |
|------------|------------|-------|
| `/ci reload` | Перезагружает config, YAML-предметы, бонусы за наборы, Java-предметы, команды, плейсхолдеры и модули | `dcustomitems.reload` |
| `/ci validate` | Проверяет рецепты YAML-предметов на ошибки | `dcustomitems.reload` |
| `/ci debug <id>` | Показывает тип, слот, заряды, кулдаун, рецепты и служебные данные предмета | `dcustomitems.reload` |
| `/ci backup` | Создаёт резервную копию `items/` + `config.yml` + `data.db` | `dcustomitems.reload` |
| `/ci` (без аргументов) | Печатает список подкоманд | Ничего не проверяется — справка доступна всем |

Право проверяется в самом плагине (`CustomItemsCommand`), а не только через `plugin.yml`. Это значит, что даже если команда каким-то образом отобразится в help, выполнить её без права нельзя.

### Права предметов

Ключ `permission:` задаёт, **кому** можно пользоваться предметом:

```yaml
legendary-sword:
  item:
    type: DIAMOND_SWORD
    title: '&6Легендарный меч'
  permission: 'myplugin.legendary_sword'
```

| Ситуация | Что произойдёт |
|-----------|---------------|
| У игрока есть право | Клик работает как обычно |
| У игрока нет права | Клик отменяется, игрок получает сообщение «You don't have permission to use this item.» |
| Ключа `permission:` нет | Ограничений нет — предметом пользуются все |

Право проверяется **только на клике**. То есть игрок может получить предмет, положить в сундук и не сможет им воспользоваться, пока не получит право. Само наличие предмета в инвентаре не блокируется.

Для Java-предмета то же самое делает переопределённый метод:

```java
@Override
public String getPermission() {
    return "myplugin.legendary_sword";
}
```

### Права команд на Java

Команда на Java задаёт право в конструкторе базового класса `CustomCommand`:

```java
public class HealCommand extends CustomCommand {

    public HealCommand() {
        super("heal", "Вылечить игрока", "/heal [player]", "myplugin.heal");
        //                              ↑ usage            ↑ право
    }

    @Override
    public boolean execute(CommandSender sender, String[] args) {
        // ...
        return true;
    }
}
```

| Параметр | Что это |
|----------|---------|
| Имя команды | `/heal`. Регистр не важен — имя приводится к нижнему |
| Описание | Текст в help |
| Usage | Подсказка по использованию: `/heal [player]` |
| Право | Узел права. `null` или пустая строка — **без ограничений** |

Метод `getPermissionMessage()` задаёт текст, который увидит игрок без права. По умолчанию берётся текст `commands.no-permission` из системы сообщений — его можно переопределить в `items/messages.java`.

### Права модулей

Модуль может зарегистрировать команду с правом по умолчанию `dci.<имя_команды>`:

```java
@Override
protected void onEnable() {
    // Право по умолчанию: dci.mycommand
    registerDynamicCommand("mycommand", this);

    // Или явное:
    registerDynamicCommand("myother", this, "myplugin.myother");
}
```

Право записывается в Bukkit-команду (`command.setPermission(...)`), но так как модуль реализует выполнение команды сам, **проверяйте право в коде модуля явно**:

```java
@Override
public boolean onCommand(CommandSender sender, Command command, String label, String[] args) {
    if (!sender.hasPermission("dci.mycommand")) {
        sender.sendMessage("§cНедостаточно прав.");
        return true;
    }
    // ...
}
```

Так же модуль может объявить список своих прав в своём `config.yml` — это документация, по которой вы затем раздаёте права:

```yaml
# plugins/DC-CustomItems/items/my-module/config.yml
name: "My Module"
version: "1.0"
enabled: true

commands:
  - mycommand

permissions:
  - mymodule.use
  - mymodule.admin
```

## Как проверяется право предмета

Порядок при клике по предмету:

1. Плагин достаёт ID предмета из служебных данных (`PersistentDataContainer`).
2. Если у предмета задан `permission:` — плагин проверяет право игрока.
3. Нет права → клик отменяется, выводится сообщение `items.no-permission`, обработка **останавливается**: ни действия, ни триггеры, ни эффекты не выполняются.
4. Есть право → клик обрабатывается дальше: кулдаун, списание заряда, событие `CustomItemUseEvent`, действия, триггеры.

Тот же порядок работает для Java-предметов (в `ApiEventListener`).

### Право работает и без клика

То же право закрывает **все** остальные пути:

| Путь | Что происходит без права |
|------|--------------------------|
| Надевание (эффекты, атрибуты, сеты брони) | Предмет надевается, но **не даёт** эффектов и бонусов |
| Триггеры (`on_kill`, `on_pickup`, `on_damage_taken`, …) | Триггер **не запускается** |

Это значит, что предмет, раздаваемый игрокам, без `permission:` даёт всем
одинаковые бонусы. Всегда ставь `permission:` на такие предметы.

> Команда `give:` выдаёт предмет независимо от прав — но воспользоваться
> его бонусами без права не получится.

## Как проверяется право команды

Порядок при вызове команды:

1. Команда находится в реестре (по имени или алиасу).
2. Проверяется право: `CustomCommand.hasPermission(sender)`.
3. Нет права → игрок получает `getPermissionMessage()` и команда **не выполняется**. Вызывается `execute()`, но не выполняется — команда возвращает `true` (Bukkit считает, что ошибки не было).
4. Есть право → вызывается ваш `execute(...)`.

То же правило действует для **автодополнения** (Tab): если права нет, подсказки не показываются.

## Как выдать право только одному предмету

Право пишется в ключе `permission:` внутри описания предмета. Название узла — любое, главное, чтобы оно не совпало с чужим.

```yaml
# items/legendary.yml
legendary-sword:
  item:
    type: DIAMOND_SWORD
    title: '&6Легендарный меч'
  permission: 'myplugin.item.legendary_sword'

vip-amulet:
  item:
    type: GOLDEN_APPLE
    title: '&eVIP-амулет'
  permission: 'myplugin.item.vip_amulet'
```

Выдача:

```bash
# Один предмет одному игроку
/lp user Steve permission set myplugin.item.legendary_sword true

# Группе «легенды»
/lp group legends permission set myplugin.item.legendary_sword true
```

Правила:

| Правило | Подробности |
|---------|--------------|
| Один предмет — одно право | Каждый предмет со своим `permission:` получает свой узел |
| Право проверяется на клике | Не при выдаче и не при надевании |
| Без ключа `permission:` | Предмет доступен всем |
| Java-предмет | То же самое через `getPermission()` |

Если предметов много, удобно сделать **иерархию имён**:

```yaml
# Универсальное право на любую «легендарку»
permission: 'myplugin.item.legendary'
# Право только на один конкретный меч
permission: 'myplugin.item.legendary_sword'
```

В LuckPerms иерархию удобно раздавать через группы, а конкретные предметы — точечно.

## Примеры с LuckPerms

Установите [LuckPerms](https://luckperms.net/), затем:

```bash
# --- Право администратора -----------------------------------------
# Выдать право на /ci reload конкретному игроку
/lp user Steve permission set dcustomitems.reload true

# Создать группу «модераторы» с правом на /ci
/lp group moderators permission set dcustomitems.reload true
/lp group moderators info

# Выдать группу игроку
/lp user Steve parent add moderators

# --- Права предметов ----------------------------------------------
# Один предмет — одному игроку
/lp user Steve permission set myplugin.item.legendary_sword true

# Один предмет — группе
/lp group vip permission set myplugin.item.vip_amulet true
/lp user Steve parent add vip

# --- Несколько предметов сразу ------------------------------------
/lp group legends permission set myplugin.item.legendary_sword true
/lp group legends permission set myplugin.item.legendary_bow true
/lp group legends permission set myplugin.item.legendary_staff true

# --- Права команд модулей -----------------------------------------
/lp group admins permission set dci.mycommand true
/lp group admins permission set dci.balance.others true
/lp group admins permission set dci.eco true

# --- Полный доступ (осторожно!) -----------------------------------
/lp user Steve permission set '*' true

# --- Убрать право --------------------------------------------------
/lp user Steve permission unset dcustomitems.reload

# --- Посмотреть, что есть у игрока --------------------------------
/lp user Steve info
/lp verbose on   # после этого плагин пишет в чат, почему проверка права прошла или нет
```

Полезная команда для отладки — `/lp verbose on`: после неё плагин пишет в чат игрока, какое право проверялось и почему проверка не прошла.

Без плагина прав (например, на тестовом сервере) проще всего использовать оператора:

```bash
/op Steve
/deop Steve
```

## Права по умолчанию самого плагина

В `plugin.yml` плагин объявляет ровно одно право:

```yaml
permissions:
  dcustomitems.reload:
    description: Reload plugin
    default: op
```

| Что это значит | Подробности |
|----------------|--------------|
| `default: op` | Только операторы имеют это право из коробки |
| Остальным нужно выдать вручную | Например, через LuckPerms |
| Команда `/ci` и её алиас `/customitems` | Требует `dcustomitems.reload` |

Поэтому типичная картина: игрок-оператор пишет `/ci reload`, обычный игрок получает отказ.

## Подводные камни

| Проблема | Причина | Что делать |
|----------|---------|------------|
| `/ci reload` не работает | Нет права `dcustomitems.reload` | Выдайте право или сделайте игрока оператором |
| `/ci` не предлагает подкоманды | Так и задумано: справка доступна всем, а вот сама команда — нет | Добавьте право |
| Игрок не может использовать предмет | Не хватает права из `permission:` | Выдайте узел из YAML |
| Предмет работает, а эффекты не применяются | Эффекты требуют, чтобы предмет был **в слоте активации** | Положите предмет в нужный слот — см. [Предметы в YAML](03-yaml-items.md) |
| Команда модуля доступна всем | Модуль не проверяет право в коде | Добавьте `sender.hasPermission("dci.<имя>")` в обработчик |
| Право не работает, хотя выдано | Опечатка в имени узла | Имена чувствительны к регистру: `myplugin.Use` ≠ `myplugin.use` |
| `customitems.admin` ничего не даёт | Узел не объявлен, а сообщение выводится только при `update-available: true` в конфиге | Это служебное право; на основную работу оно не влияет |
| Игрок видит предмет, но не может его взять | Предмет запрещён в этом мире (`disabled-worlds`) | Это не право, а ограничение мира — см. [Предметы в YAML](03-yaml-items.md) |
